# 🎓 Mood

**Mood** — приложение для студентов НИУ МЭИ (ts.mpei.ru): расписание, домашние
задания и объявления группы, личный кабинет БАРС (оценки, пропуски, приказы,
стипендия, книги НТБ, рейтинг) и превью корпоративной почты ОСЭП.

Состоит из двух клиентов на одной базе:

- 📱 **PWA** — основное приложение. Ставится на домашний экран телефона,
  работает в полноэкранном режиме, с офлайн-оболочкой и кэшем расписания. Вход —
  логином и паролем БАРС; Telegram для входа **не нужен**.
- 🤖 **Telegram-бот** — только поддержка: ссылки на PWA, установку, канал и
  `@mood_mpei_sup`. Привязки аккаунта и уведомлений в Telegram больше нет.

Проект — **два независимых процесса Node.js**: приложение (API + уведомления) и
тонкий Telegram-бот поддержки. Они не делят память и не импортируют друг друга.

## ✨ Возможности

### 📱 Веб-приложение (PWA)

- **Расписание группы** с официального портала `ts.mpei.ru`: недельная сетка
  Пн–Вс, свайп дней и недель, «Перерыв», карточка пары с заданием —
  кликабельна целиком, вложенные ссылки и кнопки работают отдельно.
- **Обновление расписания жестом**: потянуть ленту пар вниз, когда она в самом
  верху (pull-to-refresh, force-запрос). Кнопки «Обновить» в интерфейсе нет —
  данные обновляются сами по кэшу и при возврате в приложение.
- **Быстрый переход по датам**: кнопка «Сегодня» и календарь с горизонтом
  ±180 дней в шапке расписания (сегодня, выбранный день, точки на днях с
  парами; дата вне окна выгрузки даёт пояснение, а не пустой экран).
- **Домашние задания**: форма добавления, привязка к будущей паре, предметные
  сокращения («матан», «инфа», «физра» …), список по предмету.
- **«Важное»** — объявления группы с заголовком, текстом и файлами.
- **Файлы**: фото открываются во встроенном просмотрщике (`InAppBrowser`), PDF —
  системным просмотрщиком в отдельной вкладке, прочие документы отдаются системе
  («Поделиться»/сохранение).
- **Личный кабинет БАРС**: успеваемость (средневзвешенный балл по КМ, рейтинг,
  распределение оценок 5/4/3/2), пропуски, приказы, стипендия, книги НТБ.
- **Детали по тапу**: «Задолженности», «Рейтинг» и «Пропуски» открываются
  нижними листами — конкретные двойки за КМ, семь разделов рейтинга и разбивка
  пропусков по предметам, без ухода с вкладки.
- **Калькулятор оценок**: выбираешь предмет, двигаешь цель 2.0–5.0 и видишь
  минимальные баллы за оставшиеся КМ; есть режим «а если получу X» и ручные
  пороги для прогноза оценки. Считается по весам КМ, ничего не сохраняется.
- **Почта ОСЭП**: превью непрочитанных писем.
- **Самостоятельный вход** логином и паролем БАРС (без Telegram), поддержка 2FA.
- **Юридические согласия**: на входе — обработка ПДн, передача данных
  одногруппникам и пользовательское соглашение; push — отдельной необязательной
  галочкой. Тексты и версии — `backend/legal/`, `pwa/public/legal/`. Для уже
  вошедших при повышении версии показывается гейт.
- **Гостевой режим**: только расписание без БАРС — группа и имя/псевдоним.
  Гость видит пары и детали занятия, не имеет доступа к ДЗ, оценкам, почте и
  уведомлениям; учитывается в общей статистике с пометкой «гость».
- **Установка на телефон**: кнопка установки на Android, отдельный пошаговый гайд
  для iOS (только Safari, «На экран Домой»).
- **Уведомления в приложении**: центр уведомлений по колокольчику в шапке —
  вся история и фильтры по типам; события (оценки, письма, приказы, стипендия)
  с деталями, по почте — только количество новых писем. Новое уведомление
  показывается полноэкранно, поэтому в истории нет деления на прочитанные и
  непрочитанные.
- **Кабинет**: почта первой строкой, учёба в раскрывающихся секциях
  (стипендии, приказы, библиотека НТБ), документы и согласия — такой же
  свёрнутой строкой с бейджем непринятых, настройки push и темы, контакты и код.
- **Удаление аккаунта** — ссылка в подвале «Кабинета», с подтверждением;
  стирает запись, файлы, созданные задания, историю и статистику.
- **Три уровня скорости**: мгновенный старт из `localStorage` (stale-while-
  revalidate), фоновое обновление, предзагрузка файлов.

### 🤖 Telegram-бот поддержки

Telegram больше не платформа приложения. Бот оставлен как канал поддержки и
установки:

- 👋 `/start` — ссылка на PWA, `📱 iOS` / `🤖 Android`, канал, поддержка, GitHub;
- 📦 Android получает APK, если он собран на сервере;
- 💬 кнопка «Поддержка» ведёт в `@mood_mpei_sup`;
- 💾 локальный список тех, кто запускал бота (`bot-subscribers.json`), и
  рассылка по нему скриптом `tg/broadcast.mjs` (например, новым APK);
- никакой привязки аккаунта, уведомлений, админки и данных студента.

Уведомления (оценки, письма, приказы, стипендия) приходят только в приложение:
Web Push + центр уведомлений. Включение — «Кабинет → Настройки приложения →
Push-уведомления»; если push не включён, приложение напоминает раз в день.

### 🔔 Уведомления

- **в приложении** — колокольчик в шапке и лента уведомлений: вся история и
  фильтры. Новое событие всплывает на весь экран, а в истории все карточки
  выглядят одинаково — без отметок прочитанного. Детали оформлены по типу:
  цветная иконка, дисциплина, чип КМ, крупный балл и дельта (`КМ2: 15 (+5)`),
  номер/дата приказа, факт назначения или отмены стипендии; по почте
  показывается только количество новых писем (содержимое не читается);
- новые **баллы** (только рост или новая закрытая КМ, снижение не уведомляет);
- новые **письма** ОСЭП (количество, без темы и отправителя);
- новые **приказы**;
- **назначение или отмена** стипендии (смена типа или периода не уведомляет).

Опрос фоновый, раз в 20 минут в активные часы (8–23 МСК), с паузой между
пользователями (анти-бан МЭИ). Подробности — в разделе
[Фоновые уведомления](#-фоновые-уведомления).

## 🏗 Архитектура

Проект — **два процесса Node.js**, и граница между ними проходит по данным.

```text
        ┌──────────────── бот: node dist/bot.js ─────────────────┐
        │                                                        │
Telegram ─► grammY long polling ─► botEngine ─► pwaView ─► ответ │
        │                                     APK из tg/apk/     │
        └────────────────────────────────────────────────────────┘
         ни базы, ни API, ни БАРС/OWA, ни ключей шифрования

        ┌──────────── приложение: node dist/app.js ──────────────┐
        │                                                        │
PWA ──► nginx/Vite ──► Fastify /api/* ──┬─► db/storage (SQLite)  │
        (X-PWA-Token)                   ├─► scheduleCache ──► ts.mpei.ru
                                        ├─► BarsService ──► bars.mpei.ru
                                        ├─► OwaMailClient ──► mail.mpei.ru/owa
                                        └─► barsSnapshotCache (20 мин)
        │                                                        │
        │  barsNotifier (20 мин) ─► БАРС+OWA ─► Web Push ─► браузер │
        │  ночной отчёт, уборка диска                             │
        └────────────────────────────────────────────────────────┘
```

Ключевые решения:

- **Бот и приложение — разные процессы и разные systemd-юниты.** Бот собирается
  в один самодостаточный файл `dist/bot.js` (зависимости внутри бандла) и не
  импортирует ни `backend/`, ни `db/`. Приложение — `dist/app.js`.
- **У бота нет доступа к персональным данным.** Он не открывает базу, не знает
  ключей шифрования и не поднимает API; ему нужны только `TELEGRAM_BOT_TOKEN` и
  `PWA_URL`. `npm run check:bot` проверяет, что в бандл не просочился серверный
  код. Поэтому бота можно держать на другом сервере.
- **API и нотификатор — один процесс и одни сервисы.** `backend/server/`
  обращается к тем же `userStore`, `scheduleCache`, `BarsService`,
  `OwaMailClient`, что и нотификатор. API поднимается только если задан
  `API_PORT` (см. `backend/server/main.ts`).
- **Статику раздаёт не сервер.** В `backend/server` нет `@fastify/static`:
  фронтенд живёт на nginx, в dev — на Vite; API отдаёт только `/api` и `/health`.
- **Авторизация PWA — собственный токен** в заголовке `X-PWA-Token`
  (HMAC-SHA256 + проверка хэша токена в записи). Ни JWT, ни cookie, ни `initData`.
- **Снимок БАРС в памяти** (`barsSnapshotCache`) обслуживает разделы ЛК одним
  походом в МЭИ: TTL 20 минут, stale-while-revalidate.
- **Всё время — `Europe/Moscow`** независимо от часового пояса сервера.

## 🔑 Идентификация и вход

Два клиента — бот и PWA — работают с **одной записью** пользователя.

- **`userId`** (UUID) — идентификатор человека, единый для обоих клиентов.
- **`barsLoginHash`** = `sha256` от нормализованного логина БАРС — ключ связи.
  Один аккаунт БАРС = одна запись, поэтому им можно пользоваться и в боте, и в
  приложении одновременно. Привязка Telegram **не** блокирует вход в PWA.

Вход в приложение — **только логин и пароль БАРС**. Отдельной «регистрации» нет:
`POST /api/auth/login` заводит запись, если её ещё нет. Перед отправкой логина
приложение требует три обязательных согласия (обработка ПДн, передача данных
одногруппникам, пользовательское соглашение) и отдельно предлагает согласие на
push. Версии документов сервер берёт из `backend/legal/registry.ts`; клиент не
может прислать свою версию. Токен PWA живёт 90 дней, хранится в `localStorage` и
едет в каждом запросе заголовком `X-PWA-Token`.

## 🔐 Авторизация в БАРС

### Вход в PWA

1. Антибрутфорс: `checkLoginAllowed` — при блокировке в БАРС не ходим.
2. Поиск существующей записи по `barsLoginHash` (вход в уже созданный аккаунт
   разрешён).
3. `startLoginAttempt`: `new BarsClient()` + `login({ on2FACodeNeeded })` в фоне,
   гонка исходов: `done` / `two_factor` / таймаут 45 с.
4. Ошибка/неверный пароль → 401 `invalid_credentials`.
5. Успех → сохранение профиля и кредов.

Креды (логин и пароль) шифруются раздельно. `2FA` доносится до висящего промиса
входа (`POST /api/auth/2fa`, TTL 10 мин); ожидание на клиенте — 5 минут.
Попытка 2FA привязана к клиенту, который начинал вход: чужой `challengeId` не
завершит и не сорвёт вход. Повторный вход всегда создаёт новую попытку (новое
СМС) — переиспользования старой нет; неверный код учитывается лимитером.
На nginx для login/register/2fa/refresh/guest — 30 запросов/мин с IP.

### Полный вход БАРС — пять шагов

| Шаг | Действие |
|---|---|
| `[1/5]` | открытие `/bars_web/`; если уже дашборд — извлечь профиль |
| `[2/5]` | `POST` формы: скрытые поля + логин + пароль |
| `[3/5]` | разбор `af2_code_send` и запрос кода подтверждения |
| `[4/5]` | ожидание кода (`on2FACodeNeeded`) |
| `[5/5]` | `POST` кода; проверка, что страница стала дашбордом |

Сессия сохраняется файлом с правами `0600` (флаг `wx`, `O_EXCL`).

### Антибрутфорс-лимитер

`backend/utils/loginLimiter.ts` — две оси: по адресу клиента и по логину БАРС.

| Параметр | Значение |
|---|---|
| `MAX_FAILURES` | 5 |
| `WINDOW_MS` / `BLOCK_MS` | 15 мин / 15 мин |
| `MAX_BLOCK_MS` | 6 ч |
| Рост блокировки | ×2: 15 → 30 → 60 → 120 → 240 → 360 мин |

Состояние только в памяти процесса, убирается раз в 5 минут.

### Токен PWA

Формат: `base64url(userId).base64url(expiresAt).base64url(HMAC-SHA256)`, TTL 90
дней. Сервер хранит **только `sha256(token)`** в записи пользователя; при выходе
отзывается ровно текущий токен. На пользователя хранится не больше **10**
токенов: новые вытесняют старые. «Сброс сессий» в админке отзывает все токены.
Секрет `PWA_AUTH_SECRET` — отдельный от ключа шифрования.

## 📅 Расписание и кэш

- **Поиск группы** — `GET /api/search?term=…&type=group`, с фолбэком
  латиница→кириллица и подсказками.
- **Загрузка** — `GET /api/schedule/group/{groupId}?start=…&finish=…`, окно
  дат **−14 … +90 дней**, таймаут 20 с.
- **Разбор** — группировка сырых пар по дням и слотам, очистка заглушек
  (`!Не определена`), извлечение преподавателей, ссылок, подгрупп.

### Кэш (`backend/scheduleCache.ts`)

| Параметр | Значение |
|---|---|
| Свежесть | до ближайшего воскресенья 00:00 МСК |
| Постоянный слой | SQLite, таблица `schedule_cache` |
| `MAX_GROUPS` | 50 в памяти (≈12 МБ), LRU |
| Ручное обновление | `force=1` очищает копию группы |

Разобранное расписание хранится в SQLite и переживает рестарт. Загрузка
**дедуплицируется**: параллельные запросы одной группы получают один промис.
Раз в неделю, в воскресенье 00:00 МСК, копия становится старой; первый запрос
группы перезагружает её. Если МЭИ недоступен, отдаётся последняя удачная
копия, а обновление повторится на следующем запросе.

## 📝 Домашние задания и «Важное»

- **ДЗ** (`db/storage/homeworkStore.ts`): привязка к **следующей** паре
  (`homeworkManager.findNextLesson`) — пары, которые уже начались, пропускаются.
  Тип (`лекция`/`практика`/`лаба`) влияет на подбор.

- **«Сделано»** (`db/storage/homeworkDoneStore.ts`, таблица `homework_done`):
  личная отметка студента, а не общая на группу. Просроченные задания отметить
  нельзя; выполненные уезжают в свёрнутую секцию внизу списка.
- **Изоляция по группе** — сравнение `trim().toLowerCase()`; пустая группа не

- **Антифлуд** — общий счётчик `30 записей/час` на пользователя (ДЗ и «Важное»
  вместе).

Ввод, редактирование и удаление живут в PWA; в боте их нет.

|---|---|
| Размер файла | 20 МБ |
| Файлов на запись | 10 |
| Хранилище пользователя | 100 МБ |
| Разрешённые типы | jpeg, png, webp, gif, heic, heif, pdf, txt |

готовит короткоживущую inline share-ссылку, чтобы Safari не блокировал открытие
как popup.

## 🗄 Хранилище данных (db)

Основное хранилище — **SQLite** (`db/data/mood.sqlite`, драйвер `better-sqlite3`,
WAL, `synchronous=NORMAL`). Процесс один, поэтому отдельный сервер БД не нужен.

- таблица `users` — по строке на пользователя, индексы по `bars_login_hash` и
  `telegram_id`; патч одного пользователя не переписывает остальных;
- таблица `records` — плоские сторы: ДЗ, «Важное», снимки, админы, bot flows;
- таблица `documents` — небольшие документы: объявления, регистрация, статистика,
  согласия;
- таблица `user_events` — история уведомлений: текстовые `details` и
  структурированные `data` для карточек (у старых записей `data` нет);
- таблица `schedule_cache` — разобранное расписание группы, недельный TTL;
- файлы остаются на диске в `db/data/files/<userId>/` (`.bin`, `.meta.json`,
  превью), в SQLite их нет.

Права: каталог `0700`, файл БД `0600`. `db/jsonStore.ts` — тонкий адаптер с
прежним API (`JsonStore`/`JsonDocument`), поэтому модули данных не переписаны.

**Миграция со старых JSON:** `npm run migrate:sqlite` при остановленном сервисе.
Старые `db/data/*.json` не удаляются — это снимок для проверки и отката;
удалять их можно только после подтверждения, что всё работает.

**Сброс базы:** `npm run reset:db` (полный, с бэкапом в `db/data/backup/<метка>/`)
и `npm run reset:users` (только таблица `users`).

## 🔒 Шифрование кредов и сессий

AES-256-GCM (`backend/utils/crypto.ts`). Шифруются:

| Что | Где |
|---|---|
| логин и пароль БАРС | `barsAuth.encryptedLogin` / `encryptedPass` |
| cookie-сессия БАРС | `barsAuth.cookiesJson` |
| cookie-сессия OWA | `owaAuth.cookiesJson` |

| Параметр | Значение |
|---|---|
| Алгоритм | `aes-256-gcm` |
| Ключ | ровно 32 байта (64 hex-символа) |
| IV | 12 байт, новый на каждое шифрование |
| Auth tag | 16 байт |

Логин, пароль и каждая cookie-сессия шифруются раздельно (у каждого свой IV/tag).
KDF нет — ключ обязан быть высокоэнтропийным. `ENCRYPTION_SECRET_KEY` и
`PWA_AUTH_SECRET` — разные ключи: утечка одного не компрометирует другой.

Cookie хранятся в формате `enc:v1:<iv>:<tag>:<ciphertext>`. Старые записи без
префикса читаются как плейнтекст и шифруются при первом сохранении; разово все
записи переводит `node dist/app.js --migrate-cookies` при остановленном сервисе
(бэкап базы перед этим обязателен). Ошибка расшифровки не роняет процесс: сессия
считается отсутствующей, пользователь входит заново.

## 📧 Почта ОСЭП (OWA)

IMAP `mail.mpei.ru:993` режется Forefront TMG (RST на ClientHello), поэтому почта
читается через веб-интерфейс `mail.mpei.ru/owa` (FBA-вход + `service.svc`).

- Вход — форма `CookieAuth.dll?Logon` («частный компьютер»).
- `service.svc` требует HTTP-заголовок `Action` с именем операции и JSON-типы
  с суффиксом `:#Exchange` (`RequestServerVersion: Exchange2013`); иначе сервер
  отвечает 500 (`SerializationException`).
- Первый служебный запрос может получить **449** без `X-OWA-CANARY`: сервер
  присылает canary в ответе, клиент повторяет запрос уже с ним (один повтор).
- Счётчики и список писем — `service.svc?action=GetFolder` / `FindItem`.
- Сессия OWA хранится **отдельно** от БАРС (`owaAuth`); креды — те же (логин БАРС).
- Один клиент OWA на пользователя (`owaClientRegistry`): общий cookie jar и
  очередь, чтобы `/api/mail` и нотификатор не выбивали сессии друг друга.
- Ошибки: `MailUnreachableError` → 503 «нужен VPN МЭИ», `MailTimeoutError` → 504.
  `MailAuthError` → 409 `mail_reauth_required` с подтипом `reason` (сессия OWA
  сбрасывается, БАРС и PWA-токены не трогаются). Подтипы:
  `invalid_credentials`, `no_session_cookie`, `returned_login_page`,
  `broken_form`, `session_expired_after_relogin`, `two_factor_required`.
- Сессия проверяется и перелогинивается один раз при 401; заголовки (в том числе
  `X-OWA-CANARY`) на повтор собираются заново. 2FA не обрабатывается
  интерактивно — такой вход честно помечается `two_factor_required`.

В интерфейсе — только **превью** непрочитанных писем, которое наполняет фоновый
нотификатор; чтение писем — на `mail.mpei.ru`.

## 🔔 Фоновые уведомления

`backend/services/notifications/barsNotifier.ts`.

| Параметр | Значение |
|---|---|
| `POLL_INTERVAL_MS` | 20 мин |
| Активные часы | 8–23 МСК |
| Пауза между пользователями | 2.5 с + джиттер 0.5 с |
| Первый прогон | через 30 с после старта |
| Разрыв круга | 5 сетевых сбоев подряд |

В круг берутся авторизованные в БАРС пользователи, у кого `pushEnabled !== false`
и есть хотя бы одна подписка. Telegram в доставке не участвует: единственный
канал — **Web Push (VAPID)**. Подписки браузеров хранятся в
`StoredUser.pushSubscriptions` (до 10 устройств), мёртвые (404/410) удаляются
автоматически. Endpoint проверяется по allowlist (FCM, Mozilla, Apple, WNS) —
закрыт blind SSRF; отправка с таймаутом 8 с, чтобы зависший сервис не блокировал
цикл и админскую рассылку. Payload содержит только тип события, без оценок и тем
писем: он показывается на заблокированном экране. Тап открывает нужную вкладку
через `/?tab=grades|profile`. Push включается только после согласия
`push` (галочка на входе или в кабинете).

`diffSnapshots` даёт четыре события: `grade` (дельта по КМ), `mail` (письма с
`uid > prev`), `order` (рост числа приказов), `scholarship` (смена статуса).
При истечении сессии БАРС — `clearAuth` + снимок + `forgetBarsClient`.

## 🔧 Переменные окружения

Секретов два набора, и они не должны пересекаться: приложению нужны ключи и
API, боту — только токен и адрес.

```env
# --- Приложение (dist/app.js): /opt/mood/.env ---
ENCRYPTION_SECRET_KEY=      # AES-256-GCM для кредов БАРС, 64 hex
PWA_AUTH_SECRET=            # секрет PWA-токенов, 64 hex (npm run pwa:setup)
PWA_URL=                    # публичный HTTPS-адрес
API_PORT=3000               # без него REST API не поднимается
API_HOST=127.0.0.1
ADMIN_BARS_LOGINS=          # логины БАРС админов через запятую
VAPID_PUBLIC_KEY=           # Web Push (npx web-push generate-vapid-keys)
VAPID_PRIVATE_KEY=
VAPID_SUBJECT=mailto:noreply@mood.local

# --- Бот (dist/bot.js): /opt/mood-bot/bot.env ---
TELEGRAM_BOT_TOKEN=         # от @BotFather
PWA_URL=                    # кнопка «Открыть Mood»
# MOOD_APK_DIR=/opt/mood-bot/tg/apk
```

**Отладка:** `API_PERF_LOG=1` (все запросы API), `?perf=1`/`mood_perf`
(клиентские замеры), `?debug=1` (диагностика), `OWA_DEBUG=1` (логи OWA),
`OWA_TLS_INSECURE=1` (отключить проверку TLS для самоподписанного сертификата),
`OWA_BASE_URL=http://127.0.0.1:PORT` (подменить origin OWA, для тестов/отладки),
`NOTIFIER_POLL_MS=30000` (временно ускорить цикл нотификатора и интервалы
источников без пересборки; по умолчанию 20 мин).

| Процесс | Нет переменной | Что будет |
|---|---|---|
| приложение | `ENCRYPTION_SECRET_KEY` | предупреждение; креды БАРС не сохранятся |
| приложение | `PWA_AUTH_SECRET` | предупреждение; вход в приложение невозможен |
| приложение | `API_PORT` | API не поднимается, живёт только нотификатор |
| приложение | `PWA_URL` | CORS без origin, ссылки на приложение скрыты |
| приложение | `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | push-канал выключен |
| бот | `TELEGRAM_BOT_TOKEN` | процесс завершается с ошибкой |
| бот | `PWA_URL` | кнопки «Открыть Mood» нет |

Неверный **формат** ключа (не 64 hex) останавливает процесс приложения на
старте: лучше не подняться, чем молча ломаться на первом шифровании.

## 🚢 Деплой

### systemd (рекомендуется)

Готовые файлы: `backend/deploy/mood.service` (приложение),
`backend/deploy/mood-bot.service` (бот) и `backend/deploy/journald.conf`.

На проде RU бот не запущен: там только `mood.service` (`dist/app.js`).
Блок про `mood-bot` нужен, если бот поднимают на отдельном хосте.

```bash
npm ci && npm run build && npm run apk:bot

# --- приложение: API + нотификатор ---
useradd --system --home /opt/mood --shell /usr/sbin/nologin mood
chown -R mood:mood /opt/mood && chmod 700 /opt/mood/db/data && chmod 600 /opt/mood/.env
cp backend/deploy/mood.service /etc/systemd/system/mood.service

# --- бот: только ссылки, отдельный пользователь и каталог ---
useradd --system --home /opt/mood-bot --shell /usr/sbin/nologin mood-bot
install -d -m 700 -o mood-bot -g mood-bot /opt/mood-bot/dist /opt/mood-bot/tg/apk
install -m 600 -o mood-bot -g mood-bot /dev/null /opt/mood-bot/bot.env
#   в bot.env: TELEGRAM_BOT_TOKEN, PWA_URL, при необходимости MOOD_APK_DIR
cp dist/bot.js /opt/mood-bot/dist/
cp tg/apk/*.apk /opt/mood-bot/tg/apk/     # если APK собран
cp backend/deploy/mood-bot.service /etc/systemd/system/mood-bot.service

mkdir -p /etc/systemd/journald.conf.d && cp backend/deploy/journald.conf /etc/systemd/journald.conf.d/mood.conf
systemctl daemon-reload && systemctl enable --now mood mood-bot
```

`dist/bot.js` — самодостаточный бандл: на сервере с ботом не нужны ни
`npm ci`, ни `node_modules`, ни база. Достаточно Node 20 и двух переменных в
`bot.env`. Юнит бота работает от отдельного пользователя, с `ProtectSystem=strict`
и без доступа к домашнему каталогу — компрометация бота не даёт ключей
шифрования и персональных данных.

При переезде со старых JSON (один раз): остановить сервис, выполнить
`npm run migrate:sqlite`, затем запустить сервис. Старые `db/data/*.json`
остаются на месте до проверки — их удаление отдельное решение.

Лимиты памяти выставлены в юнитах: приложение — `--max-old-space-size=768`,
`MemoryMax=1536M`; бот — 96 и 160 МБ. Падение от OOM тогда видно в
`journalctl`, а не приходит молчаливым `SIGKILL`.

### Статика PWA

```bash
npm run pwa:build
sudo rsync -a --delete pwa/dist/ /var/www/mood-pwa/
```

`rsync`, а не `cp -r dist/*`: манифест сборки лежит в `pwa/dist/.vite/` и скрыт
от шаблона `*`, без него офлайн-оболочка Service Worker остаётся без бандлов.

⚠️ **`--delete` не должен удалять старые `assets/*.js`.** У клиента `index.html`
(и в Service Worker, и в браузерном кэше) ссылается на хэшированные чанки
предыдущей сборки. Если их удалить, приложение открывается **белым экраном** до
обновления Service Worker. Поэтому выкладываем так:

```bash
rsync -a --delete --exclude 'assets/***' pwa/dist/ <сервер>:/var/www/mood-pwa/
rsync -a pwa/dist/assets/ <сервер>:/var/www/mood-pwa/assets/
sudo find /var/www/mood-pwa/assets -type f -mtime +30 -delete   # чистим только старое
```

В nginx у `/index.html`, `/sw.js` и `/manifest.webmanifest` стоит
`open_file_cache off`: иначе `open_file_cache` до минуты отдаёт предыдущий
`index.html` из памяти воркера, и релиз «не приезжает» сразу.

**Откат.** Перед выкатом сохраняйте предыдущие артефакты — тогда откат не
требует пересборки:

```bash
# на сервере, перед заливкой новой версии
cp ~/mood/dist/app.js ~/mood/dist/app.js.bak-$(date +%s)
cp /opt/mood-bot/dist/bot.js /opt/mood-bot/dist/bot.js.bak-$(date +%s)
sudo rsync -a /var/www/mood-pwa/ /var/www/mood-pwa.bak-$(date +%s)/

# откат
cp ~/mood/dist/app.js.bak-<метка> ~/mood/dist/app.js
sudo cp /opt/mood-bot/dist/bot.js.bak-<метка> /opt/mood-bot/dist/bot.js
sudo rsync -a --delete /var/www/mood-pwa.bak-<метка>/ /var/www/mood-pwa/
sudo systemctl restart mood mood-bot
```

Секреты при откате не затрагиваются: `.env`, `bot.env` и `mood.keystore` живут
отдельно и в артефакты сборки не попадают.
Шаблоны nginx — `pwa/nginx.conf.example` и `backend/deploy/mood-user-nginx.conf`.
Подробный runbook прямого деплоя — `backend/deploy/README-direct.md`.

## 📱 APK (TWA)

Android-приложение — **Trusted Web Activity** (Bubblewrap): тонкая нативная
оболочка, которая открывает `PWA_URL` в Chrome без адресной строки. Google Play
не используется, APK раздаётся файлом (Telegram). iOS этот APK не подходит —
там Safari → «Поделиться» → «На экран Домой».

### Когда пересобирать APK

**НЕ нужно** при любых изменениях PWA: код, стили, контент, API, расписание.
TWA каждый запуск грузит сайт с сервера — достаточно обычного деплоя статики.

**Нужно** только если меняется сам APK:
- `manifest.webmanifest`: имя, `short_name`, иконки, `theme_color`,
  `background_color`, `start_url`, `display`, `orientation`;
- `applicationId` (`ru.mpei.mood` — навсегда);
- keystore (перегенерация = новое приложение, обновить поверх нельзя);
- `android/twa-manifest.json` (домен, версия, настройки TWA).

### Keystore — бэкап обязателен

```bash
npm run apk:keystore      # идемпотентно: существующий ключ не перегенерирует
```

Создаёт `mood.keystore` (RSA 2048, validity 10000 дней, alias `mood`) и дописывает
`APK_KEYSTORE_PASSWORD` / `APK_KEY_PASSWORD` / `APK_KEY_ALIAS` в `.env`.
`mood.keystore` и `*.keystore` — в `.gitignore`.

> ⚠️ **Потеря keystore или пароля = новый APK встанет как ДРУГОЕ приложение.**
> Обновить установленное поверх нельзя, пользователям придётся удалять старое.
> Сделайте бэкап `mood.keystore` **и** паролей из `.env` в защищённое место
> (менеджер секретов, зашифрованный архив вне репозитория).

### Иконки и assetlinks

```bash
npm run apk:icons         # 48/72/96/144/192/512 any + 512 maskable (sharp)
npm run apk:assetlinks    # SHA-256 из keystore → pwa/public/.well-known/assetlinks.json
```

`assetlinks.json` **не редактируется руками**: отпечаток берётся из keystore.
После смены ключа — только `npm run apk:assetlinks` и деплой статики.

### Nginx: Content-Type обязателен

Без корректного `Content-Type: application/json` Android не подтвердит связь
домена и APK — приложение откроется **с адресной строкой**, при этом всё
остальное будет работать. Это тихая поломка.

Сниппет — `backend/deploy/nginx-assetlinks.snippet.conf` (уже добавлен в
`pwa/nginx.conf.example`). Применить на VPS:

```bash
sudo cp backend/deploy/nginx-assetlinks.snippet.conf /tmp/   # вставить блок в server{}
sudo nginx -t && sudo systemctl reload nginx

curl -sI https://<домен>/.well-known/assetlinks.json | grep -i content-type
# ожидаем: content-type: application/json
```

### Сборка

Однократно нужны JDK 17 и Android SDK (Bubblewrap 1.27 ждёт
`build-tools;36.1.0`, `platforms;android-36`):

```bash
brew install openjdk@17
brew install --cask android-commandlinetools
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.1.0"
```

Пути JDK/SDK прописываются в `~/.bubblewrap/config.json`
(`jdkPath` — сам `.jdk`-бандл, Bubblewrap добавит `Contents/Home` сам).

```bash
npm run apk:init          # android/twa-manifest.json из .env (--force для обновления)
npm run apk:build         # Bubblewrap: Gradle + подпись → apk/mood-<version>.apk
npm run apk:verify        # apksigner + сверка SHA-256 с assetlinks.json и package
```

`apk:build` неинтерактивен: пароли Bubblewrap берёт из
`BUBBLEWRAP_KEYSTORE_PASSWORD`/`BUBBLEWRAP_KEY_PASSWORD` (скрипт подставляет их
из `APK_*`). В `android/` в git лежит только `twa-manifest.json`; Gradle-проект
генерируется и в репозиторий не попадает (см. `android/.gitignore`).

### Раздача в Telegram

APK (~1–2 МБ) отправляется файлом в канал/бот. Минимальная версия — **Android
7.0** (`minSdk 24`: требование `androidbrowserhelper`). Получатель открывает
файл, разрешает установку из неизвестных источников (Android 8+:
«Установить неизвестное приложение» для Telegram/файлового менеджера),
устанавливает.
Обновление — тем же путём: новый APK с той же подписью ставится поверх.

Бот берёт файл из `tg/apk/` (не из общего `apk/`), поэтому после сборки APK
скопируйте его:

```bash
npm run apk:bot     # apk/*.apk → tg/apk/, старые версии удаляются
```

В git бинарник не попадает: `tg/apk/*.apk` в `.gitignore`, `deploy.sh` копирует
файл на сервер бота. Если файла нет, бот показывает инструкцию установки PWA.

Черновик сообщения:

> **Mood для Android**
> Расписание, задания, оценки и почта МЭИ — в одном приложении.
> Скачать: `mood-1.0.0.apk` (прикрепить файлом)
> Установка: откройте файл → «Разрешить установку» → «Установить».
> iPhone: APK не подходит — откройте https://<домен> в Safari → «Поделиться» →
> «На экран Домой».

### Если TWA открылся с адресной строкой

1. `curl -sI https://<домен>/.well-known/assetlinks.json` — 200 и
   `content-type: application/json`;
2. package и SHA-256 в файле совпадают с `npm run apk:verify`;
3. APK установлен из того же домена, что в assetlinks (не переименованный
   пакет и не пересобранный другим ключом);
4. Chrome обновлён; на некоторых прошивках (MIUI/EMUI) проверка кэшируется —
   переустановка приложения или очистка данных Chrome помогает.

## 🛠 Админка в PWA

Отдельной страницы `/dev/` больше нет. Все служебные действия живут в
«Кабинете»: шестерёнка рядом с колокольчиком видна только администратору.

| Раздел | Что делает |
|---|---|
| Статистика | сегодня / вчера / неделя / месяц / дата; карточки, активность по часам, платформы |
| Рассылка | всем или лично; каналы: лента и Web Push (Telegram в доставке не участвует) |
| Пользователи | поиск, карточка, сброс сессий БАРС/OWA и всех PWA-токенов, удаление с подтверждением |
| Объявления | очередь модалок и записей в центре уведомлений |
| Диагностика | аптайм, память, диск, нотификатор, принудительный прогон, журнал действий |
| Обслуживание | ручная уборка файлов и кэшей |
| Регистрация | вкл/выкл новых аккаунтов |
| Администраторы | env-админы (только количество, логины скрыты) и назначенные из PWA |

Права: `ADMIN_BARS_LOGINS` (логины БАРС, хэшируются при старте) и назначенные из приложения. Все маршруты
`/api/admin/*` проверяют права на сервере; обычный пользователь получает 403.

Статистика за прошлые дни читается из `db/data/reports/`:
`stats-YYYY.MM.DD.json` пишется при ночном срезе, старые HTML-отчёты
разбираются один раз. Ночной срез сохраняется даже без push-подписок.
Журнал действий администратора — до 500 записей в SQLite.

## ⚡ Производительность и лимиты

Целевая машина: **1 vCPU, 4 ГБ RAM, 10 ГБ NVMe**, два процесса (приложение и
бот), ~500 DAU, пиковый онлайн 20–40.

### Замеры (на сервере, 20 параллельных, loopback)

| Маршрут | До (p95) | После (p95) | После (p50) |
|---|---|---|---|
| `GET /api/bootstrap` | **2543 мс** | **46.8 мс** | 24.0 мс |
| `GET /api/homework` | 49 мс | 57 мс | 31 мс |
| `GET /api/important` | 44 мс | 37 мс | 27 мс |

Что дало ускорение bootstrap:
- проверка сессии БАРС больше **не блокирует** ответ: значение берётся из
  5-минутного кэша (`isBarsSessionValid` + single-flight), при промахе отдаётся
  `sessionValid: null` и проверка греется в фоне;
- `scheduleRange` тоже не ждёт МЭИ: из кэша группы, иначе `null` и прогрев в
  фоне (в интерфейсе это поле не используется, список грузится отдельно).

Оговорка: нагрузочный клиент работает на той же 1 vCPU, поэтому «сырой» p95
`/health` (≈280 мс) — артефакт деления ядра, а не обработчика: `/health` не
делает ничего, кроме JSON.

### Память и CPU

- `--max-old-space-size=768`, `MemoryMax=1536M`: OOM виден в journald, а не
  приходит тихим SIGKILL. RSS процесса в простое — 55–60 МБ.
- **sharp** ограничен семафором «одна задача за раз»: libvips иначе занимает
  потоки и выедает CPU у API/нотификатора на 1 vCPU.
- Кэши: расписание (LRU, 50 групп), снимок БАРС (20 мин), реестры клиентов
  БАРС/OWA (TTL 30 мин, потолок 60), кэш валидности сессии (5 мин, потолок 2000).
- SQLite с WAL: запись пользователя — одна строка, снимки — один `flush()`
  на круг, а не перезапись целых JSON-файлов.

### Диск (10 ГБ)

| Что | Лимит |
|---|---|
| Файл | 20 МБ |
| Файлов на запись | 10 |
| **Квота пользователя** | **100 МБ** (было 500) |
| Превью | ширина ≤ 1200 px, живут 30 дней |
| Отчёты HTML | 30 дней |
| Бэкапы `db/data/backup` | 7 дней |
| Свободное место для загрузки | ≥ 1 ГБ, иначе отказ |

Почему 100 МБ: 500 DAU × 100 МБ = 50 ГБ — верхняя граница, которая не влезет
целиком, но реально файлами пользуется меньшая часть; 100 МБ — это ~5 PDF по
20 МБ или десятки фото конспектов, для ДЗ и «Важного» с запасом. Дополнительно
работает ежедневная уборка: превью, «осиротевшие» файлы (записи удалены),
`.tmp`, старые отчёты и бэкапы; при занятости диска > 80 % пишется
предупреждение, при < 1 ГБ свободного — загрузка отклоняется с понятным текстом.

### Веб и инфраструктура

- PWA: «Успеваемость» и «Задания» — отдельные чанки (`React.lazy`), стартовый
  бандл уменьшился на ~18 КБ; localStorage-запись ограничена 3 МБ, иначе
  расписание могло вытеснить кэш ДЗ.
- nginx: `keepalive` к Fastify, `open_file_cache`, gzip (brotli в сборке нет),
  неизменяемый кэш `/assets/`.
- `/health` — локальный, без походов в МЭИ.

## 🍏 iOS (нативное приложение)

Отдельное приложение для iPhone на **SwiftUI**, минимальная версия — iOS 18.
Проект живёт в `ios/`; `.xcodeproj` генерируется XcodeGen и в git не попадает,
источник правды — `ios/project.yml`.

Текущая фаза — устанавливаемая оболочка: полноэкранный `WKWebView` открывает
PWA, сохраняет сессию между запусками (`WKWebsiteDataStore.default()`), уводит
внешние ссылки в `SFSafariViewController` (чужой сайт не получает доступ к
`localStorage` с токеном), скачивает файлы через системный share sheet, умеет
нативные `alert`/`confirm`/`prompt` и подстраивает оформление под тему PWA.

```bash
brew install xcodegen
cd ios && xcodegen generate && open Mood.xcodeproj
```

Сборка и установка — `ios/README.md`. Подпись — Personal Team (бесплатный Apple
ID): профиль живёт 7 дней, а push, виджеты, Share Extension и Universal Links
недоступны до покупки Apple Developer Program ($99/год) — это ограничения
Apple, а не кода.

Дальше экраны переписываются на SwiftUI по одному: вход и 2FA → расписание с
офлайн-кэшем → оценки и задания → кабинет. Серверный контракт не меняется:
тот же `/api/*`, тот же заголовок `X-PWA-Token`.

## 🛡 Безопасность прода

Прод — только RU (`mood-app.ru`). Конфиги в репозитории — `backend/deploy/`;
на сервере они лежат в `/etc/nginx/`, `/etc/systemd/system/`,
`/etc/ssh/sshd_config.d/`.

| Слой | Что сделано |
|---|---|
| SSH | только ключ, `PermitRootLogin no`, `AllowUsers spartanec`, `MaxAuthTries 3`; ufw deny incoming, fail2ban (бан 1 ч), unattended-upgrades |
| nginx | HTTP/2, TLS 1.2/1.3, HSTS, CSP, `nosniff`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`; 403 на dotfile/`*.bak`/`*.sqlite`, 404 на `/dev/`, `/dev-api/`, `/test/`; `limit_req` 30/мин на auth; share-токены не пишутся в access-log; gzip и годовой кэш ассетов |
| systemd | `ProtectSystem=strict`, `ProtectHome=read-only`, `ReadWritePaths=db/data`, `NoNewPrivileges`, `PrivateTmp`, пустой `CapabilityBoundingSet`, `MemoryMax=700M` |
| Приложение | cookie БАРС/OWA — AES-256-GCM; 2FA привязан к клиенту; push — allowlist и таймаут 8 с; не больше 10 PWA-токенов; CORS только `PWA_URL`; превью — 4 ширины; CSP без inline-скриптов |
| Деплой | не передаёт `mood.keystore`, `apk/`, `android/`, `.env.*`; keystore локально `600` |

Проверка после изменений: `/health`, `systemctl is-active mood nginx`,
`journalctl -u mood -p warning`, заголовки через `curl -I`.

## ⚠️ Известные риски и техдолг

1. `.env` содержит ключи шифрования и VAPID; cookie-сессии в SQLite
   зашифрованы, но `.env` и старые дампы/бэкапы базы — нет. Закрыты правами
   `600`/`.gitignore`, но лежат на сервере.
2. `scheduleCache` теперь постоянный (SQLite, недельное обновление), а
   `barsSnapshotCache` остаётся в памяти и не переживает рестарт.
3. Схема SQLite пока без версионирования миграций (`CREATE TABLE IF NOT EXISTS`);
   при изменении таблиц нужна ручная миграция.
4. Ротация `ENCRYPTION_SECRET_KEY`/`PWA_AUTH_SECRET` невозможна без миграции.
5. Хрупкость скрапинга: парсеры привязаны к HTML конкретной версии ЛК и к OWA.
6. `ACADEMIC_HOURS_PER_LESSON = 2` зашито константой.
7. Задолженность = только двойки; незакрытые КМ — ни в задолженность, ни в
   распределение.
8. У веб-приложения нет автотестов (вёрстку проверяет `check:layout`).
9. Нет роутера во фронтенде: ни истории, ни диплинков.
10. Антифлуд ДЗ/«Важного» и лимитер входа живут только в памяти процесса.
11. APK подписан локальным `mood.keystore`: потеря ключа/пароля означает новое
    приложение вместо обновления. Бэкап обязателен (см. «APK (TWA)»).
12. Верификация TWA тихая: неверный `Content-Type` assetlinks.json или старый
    отпечаток проявляются только адресной строкой на устройстве.
13. CSP включён (`script-src 'self'`, inline-скриптов нет, recovery вынесен в
    `/boot-recovery.js`). Политика не проверялась в реальном браузере после
    включения: при проблемах с PDF/фото смотреть `blob:`/`worker-src`.
14. `npm audit` по dev-зависимостям показывает 14 находок (high) в дереве
    `@bubblewrap/cli` (`uuid`, `node-forge`, `file-type`, `extract-zip`). Это
    инструмент сборки APK, в рантайм не попадает (`npm audit --omit=dev` — 0);
    доступного фикса без ломающего даунгрейда Bubblewrap нет.
15. Лимиты памяти (`--max-old-space-size`, `MemoryMax`) при OOM дают рестарт
    сервиса: это защита от тихого SIGKILL, но кэши и реестры в памяти теряются.
16. Brotli не включён: модуля `ngx_brotli` в системном nginx нет, работает gzip.
17. Redis/Postgres не вводились осознанно: приложение — один процесс, `db/data`
    — десятки мегабайт, кэши в памяти укладываются в 1 vCPU/4 ГБ. При переходе
    к нескольким процессам/репликам приложения понадобится общий стор — это
    отдельная задача.
18. Два процесса делят только код репозитория: бот (`dist/bot.js`) и приложение
    (`dist/app.js`) собираются и деплоятся отдельно. Общей базы у бота нет —
    это осознанная граница приватности, а не недоделка.
19. Нагрузочный замер идёт с той же 1 vCPU (клиент и сервер делят ядро),
    поэтому абсолютные p95 консервативны; для «чистых» цифр нужен внешний
    генератор нагрузки.
20. Гость задаёт `groupId/groupName` без сверки с МЭИ — можно попасть в
    материалы другой группы.
21. Файлы доступны по `requireUser` без проверки актуальных согласий.
22. Любой админ может назначить нового админа; чтение ПДн в админке не
    аудируется.
23. «Удаление аккаунта» не удаляет журнал согласий и дневные HTML-отчёты.
24. `OWA_TLS_INSECURE=1` может отключить проверку TLS к почте — в проде лучше
    не использовать.
25. `pdfjs-dist`/`react-pdf` 2023 года; `isEvalSupported: false` закрывает
    основной CVE, но зависимости стоит обновить.
